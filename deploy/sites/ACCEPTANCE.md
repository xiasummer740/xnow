## 3. 三条"不该出现"的红线

验收时如果发现以下任一条，**优先级最高**，立刻发我：

1. 客户能看到或推算出你的进货成本
2. 分站卖得比成本低，导致**你**亏钱（系统会自动抬平到成本价，只保证不亏，但客户会觉得价格和标价不符）
3. 主站 `xnow.taikon.top` 外观/价格有任何变化

补充两条已经定好、验收时可以顺手核对的行为：

4. **一个站长只能开 1 个分站**（超管不受限）。超额提示：`每位站长最多开 1 个分站（你现在已有 1 个）`

   浏览器标签显示的是站长自己的站名，不是「XNOW PRO」

### 审计过程中发现并修掉的 3 处泄露（2026-10-24 · 五十七期）

前几轮审计漏了这三处，因为它们**不含敏感词**，但一样会暴露平台身份：

| 问题 | 后果 | 修法 |
|---|---|---|
| **右下角悬浮客服指向 `t.me/Xnow001Bot`** | 客户在站长店里点客服，直接进了平台的 Telegram 群 | 分站没填客服链接就整块不显示；填了指向站长自己的 |
| **`/vip` 页是平台「至尊代理」招代理页**（¥99/月、8 折进货、佣金翻倍）| 等于在站长店里替他拉代理，还告诉客户"站长是二级代理" | 分站上路由级屏蔽 + 侧边栏入口隐藏 + 首页 VIP 模块不渲染 |
| **公开配置接口下发 `agent_discount: 0.8`** | 客户能算出平台给代理打 8 折，进而推断站长是二级代理 | 分站不下发该字段（主站保留，主站零售价本来就公开）|

> 教训：白标审计不能只搜关键词。像「平台机器人链接」「招代理页面」这类
> **功能本身**就是平台身份的东西，搜词是搜不出来的 —— 必须逐页看功能。

### 🔴 最严重的一处：分站首页源码就是平台自己的 SEO（2026-10-24 · 五十八期）

前几轮所有审计都是「打开页面看内容」，而这次发现了更上游的问题 —— **页面源码**。

| 分站路径 | 修之前返回什么 | 现在 |
|---|---|---|
| `/` 首页源码 | `title = XNOW PRO - ...`，`og:image = https://xnow.taikon.top/og-image.png`，正文里 18 处 XNOW | `title = 社媒增长服务`，无 og:image、无 canonical、**0 处 XNOW** |
| `/vpn` | 「XNOW 全球安全节点 - 高速稳定线路」= 平台的 VPN 业务页 | **404** |
| `/finance` | 「XNOW 财务大盘预览」= 平台的财务页 | **404** |
| `/en` | 「XNOW PRO SMM Panel」= 平台英文站 | **404** |
| `/404.html` | 「404 - 页面未找到 \| XNOW」 | **404** |

**为什么致命**：站长最主要的获客方式是「把链接发出去」。链接发到微信 / Telegram /
WhatsApp 时，预览卡片读的是**源码里的 og 标签**（这些爬虫不执行 JS）——
客户还没点开，就已经看到「XNOW PRO」和平台的分享图。

**修法**：构建时额外生成一份中性入口 `dist/site.html`（同一份 JS，只是 SEO 元信息中性、
favicon 换成中性图标），分站 vhost 的默认首页与 SPA 回退都指向它；
平台自己的营销页在分站 vhost 里显式 `return 404`。JS 跑起来后由前端把
title / description / og 换成**站长自己的站名**。

主站 vhost 完全没动：`/`、`/vpn`、`/finance`、`/en` 与修之前逐字相同（XNOW 出现次数 19/16/1/15）。

### 🔴 邮件兜底路径把平台广告发进客户邮箱（2026-10-24 · 六十一期）

站长第一天不会配 SMTP，这时候邮件走平台通道 —— 原来的兜底逻辑是
「没配分站 SMTP → 用平台的模板」，于是客户收到的是：

> **XNOW PRO** … 💎 升级至尊代理，佣金翻倍 …

等于平台亲自往站长的客户邮箱里塞招商广告，还当面告诉客户"你的站长是二级代理"。

**修法**：模板选择与通道选择拆开 ——
模板看「有没有站名」（有站名就用站长品牌的中性模板），通道看「有没有分站 SMTP」。

| 场景 | 修之前 | 现在 |
|---|---|---|
| 站长已配 SMTP | 站长品牌 ✅ | 站长品牌 ✅ |
| **站长没配 SMTP（走平台通道）** | **XNOW PRO 模板 + 至尊代理广告 ❌** | 站长品牌中性模板 ✅ |
| 发件地址 | 平台邮箱（无法避免）| 平台邮箱，**已在后台明确告知站长** |

实测（假 SMTP 抓包）：正文标题「阿明涨粉工作室」、正文 XNOW 命中 0 处。
发件地址仍是平台邮箱 —— 这点做不到隐藏，所以后台的提示改成了明确说明：
「不填也能用，但发件地址会是平台的邮箱，客户点开详情能看到平台域名」。

### 布局「左一个右一个」（2026-10-24 · 六十一期，祥哥当场指出）

现象：极简/杂志版式下，Hero、热门服务居中，而「三张卖点卡」和「底部 CTA」贴在页面左边。

根因（两层叠加）：

1. `.site-section` 只设了 `max-width`，这两个区块没有 `mx-auto`（其余区块有）
2. 父级是 flex 纵向容器 —— **元素一旦有 `margin: auto`，就不再被拉伸，而是收缩到内容宽度**
   于是每个区块宽度都不一样（实测同一页里出现 896 / 656 / 268 / 326 四种宽度）

修法：所有区块统一 `width: 100% + max-width: 56rem + margin: auto`；
自带背景的色带保持整幅宽，只把内部内容对齐到同一列。

实测（1440 宽）：六个区块全部 `left=269 right=1165 width=896`，色带 `0→1434` 整幅。

## 4.6 支付回调实测（方案②：钱直接进站长账户）

不需要真商户号也能验：给自己填一组测试 key，用**与 pay.js 完全相同的算法**自签回调。

| # | 场景 | 客户看到的 / 结果 | 核对 |
|---|---|---|---|
| 1 | 站长没填商户，客户点充值 | 「本站在线充值暂未开通，请联系客服充值」 | ✅ **绝不回退平台商户**（否则钱会进你账户，违背方案②）|
| 2 | 站长填了商户，客户下单 | 收款地址 = `https://bufpay.com/api/pay/<站长自己的id>`；商品名「老张涨粉铺充值」 | ✅ 用站长的商户号、站长的站名 |
| 3 | 网关回调（签名正确）| HTTP 200 `ok`；余额 50 → 60；流水「支付宝充值 — BufPay异步回调」 | ✅ 入账金额与流水一致 |
| 4 | 回调**签名伪造** | HTTP 400 `Sign Error`；余额不变 | ✅ 伪造打不进钱 |
| 5 | **同一回调重复打两次** | 第二次也回 200（让网关别再重试），但余额**不再增加** | ✅ 幂等，不会重复入账 |

⚠️ 一个容易误解的点：客户申请充值 10 元，网关实际收 10.50（5% 手续费，满 500 免），

## 十六、自有域名（自定义域名）的实测边界（74 期）

### 十六之补：真签证书这一步，已经用真实域名跑通了（75 期）

上一版这里写着"缺一个真域名，签证书这步测不了"。后来发现可以用公网通配 DNS 服务
（`nip.io` / `sslip.io`，`192-129-210-52.nip.io` 这类名字直接解析到本机 IP）做真实测试，
于是把整条链跑了一遍 —— 并且**跑出了这个功能的一个致命 bug**。

**Bug：首次签发根本不可能成功。** 所有 vhost（含全局默认）的 80 段都是
`return 301 https://...`，新域名此刻只有自签证书，LE 的 HTTP-01 跟到 HTTPS 就校验失败
→ 只能退回自签 → 站长看到"浏览器不安全"。也就是说「自有域名自动证书」这条要求，
代码逻辑上一直是个空转。

修法（已合入）：专用 ACME webroot `/var/www/acme-challenge`；vhost 的 80 段
**先放行 `/.well-known/acme-challenge/`，其余才跳转**（跳转必须写进 `location /` ——
server 层 `return` 在 rewrite 阶段就执行，location 里的例外轮不到）；
新增 `deploy/sites/fix-acme-webroot.sh` 修全局默认 server（幂等 + 备份 + 失败自还原），
并接进 `deploy-prod.sh`。

实测记录（Beta，真实公网域名）：

```
绑定 192-129-210-52.nip.io
  → {"status":"success","cert_mode":"letsencrypt","vhost":"..."}   耗时 4.4 秒
  → 证书 issuer=C=US, O=Let's Encrypt, CN=YR1   有效期 2026-10-24 → 2027-01-22
  → curl verify=0（浏览器绿锁）HTTP=200，页面标题「阿明涨粉工作室」
  → 同一个站，免费子域名 demostore.taikon.top 同时 200 / verify=0
解绑
  → vhost 0 残留、LE 证书已删除、自签 0 残留、其他站全部 200
```

顺带修掉第二个问题：**解绑时只删 vhost、不删证书**，站长换几次域名就会在
`/etc/letsencrypt/live` 堆一堆废证书，而 LE 对"同一组域名重复签发"有每周 5 张的上限，
堆到后面会签不下来。现在解绑会一并 `certbot delete` + 清理自签文件（尽力而为，不影响解绑）。

一个小提示：绑定后**立刻**访问可能还被旧 worker 服务（nginx 是优雅重载），
等 1~2 秒再刷新就对了 —— 实测踩过这个以为"没生效"。

## 十八、上游是怎么做分站的（78 期调查）+ 推广主站的三个方案

### 查到了什么

- 我们的上游是 `https://tk7188.com/api/v2`（Perfect Panel 那套面板，接口是 API v2）。
- 它首页 FAQ 原文：「为了感谢长期支持我们的会员，我们推出了**开通分站业务**和各种特别活动」
  → 分站（child panel）在它那里是一块**收费业务**。
- 同机 `/opt/xnow-flow` 是另一套东西（XNOW 云控系统：设备/任务/授权），**跟分站无关**，别搞混。
- `https://tk7188.com/child-panel` 存在但 **302 到登录页**（`?redirect=%2Fchild-panel`），
  所以分站的具体规则（价格、域名怎么绑、后台在哪）**在登录态里**，公开页面看不到。

### 这类面板（Perfect Panel）的分站模型，跟我们已实现的对得上

| 上游的做法 | 我们的对应实现 | 状态 |
|---|---|---|
| 分站是独立白标站（自己的域名、自己的外观） | 站长自己的域名/免费子域名 + 6 模板 6 色系 | ✅ 已有 |

| 分站主人**自己定零售价**（加价） | 倍数 2~100，低于成本线系统拦住 | ✅ 已有 |
| 父面板给推广人**返佣**（上游是 5%） | 我们是 10%（agent/admin） | ✅ 已有 |
| 分站本身另收月费 | 我们：¥99/月 的至尊代理资格即可开站 | ✅ 已有 |

差别：上游的分站要**另外装一套系统**、有独立后台；我们是在同一套系统里开分站，
站长管分站就回主站账号管（'我的分站'），分站上不出现任何管理入口 —— 这点比上游更省事。

### 让站长主动帮忙推广主站：三个方案（待祥哥选）

1. **返佣看板（零成本，已有机制）**：站长专属链接 `https://xnow.taikon.top/?ref=<UID>`，

## 十九、推广返佣链路：真金白银跑了一遍（79 期）

让系统以为客户真的付了钱 —— 走的是和真实支付完全相同的入账代码。

| 被邀请人（UID16，邀请人=站长 UID11）充值 ¥100 | 客户余额 0 → **100** ✅ |

## 二十、定价权交给站长：单个服务改价 + 折扣促销（80 期）

祥哥 2026-10-25 定调：
> 「分站不用奖励，他开了分站就是给其它客户用的，客户也不该知道我的网站。**但是他可以对自己的分站用户进行调价，折扣等等**。」

照这句话做了两件事：**给站长他自己的价格体系**；**把主站从分站上彻底藏掉**。

### 1. 站长价格体系（新功能）

| 能力 | 说明 |
|------|------|
| 全场倍率 | 原有能力（1~100 倍，下限受成本保护） |
| **单个服务改价** | 新表 `site_service_prices`：站长可给任一服务单独定价，没设的跟随全场倍率 |
| **折扣促销** | `sites.discount_rate / discount_label / discount_until`：可设 95/9/85/8/75 折，配宣传语，可设 3/7/30 天或长期，到期自动恢复原价 |
| 客户侧展示 | 分站首页首屏显示「🎫 开业 9 折，仅限本周」徽章（4 套版式都有），列表价与实扣价同口径 |

**成本保护（三道闸门，站长想亏本也亏不了）**
1. 定价保存时：单服务价格 < 进货价 → 直接拒，并告诉你成本线是多少；
2. 折扣保存时：`倍率 × 折扣 < 进货倍率` → 拒，并算出「最低只能打到 4 折」；
3. 下单时：售价 < 分站成本 → 自动抬平到成本（并记日志）。

## 二十三、上线演练（83 期）：用生产库副本抓到的致命缺口

### 为什么 Beta 全绿，上线仍可能全站崩

Beta 的库是空的，`sites` / `orders` 表都是 `sequelize.sync` **从零建**的 —— 字段天然齐全。
生产不一样：

| 表 | 生产现状 | 新代码期望 | 后果 |
|---|---|---|---|
| `sites` | 11 列（早期版本） | 56 列 | 站长后台、分站配置全线 500 |
| `orders` | **没有 `site_cost` 列** | 每单都要写 | **全站下单直接失败** |
| `transactions` | **没有 `site_id` 列** | 充值记录要写 | 支付回调入账失败 |

而 `sequelize.sync({ alter: false })` 只在**建表**时按模型建全，对**已存在的表一列都不会加**。
此前手工写的 3 条 `ALTER TABLE sites`（折扣相关）只补了自己那 3 列。

### 修法：启动时按「模型 vs 真实表」做差集，自动补列

`server/src/app.js` 的 `initDatabase()` 里新增一段（只 ADD 缺失列，不删不改，可重复执行）：

```
模型定义 56 个字段  ⟶  describeTable 读出真实列  ⟶  差集逐列 addColumn
```

演练实测（xnow_rehearsal = 生产库副本）：

```
[migrate] orders.site_cost 已补上
[migrate] transactions.site_id 已补上
[migrate] sites.template 已补上
... …
[migrate] 自动补列完成：新增 44 列
```

补完后在同一份**生产数据**上验证：

| 检查 | 结果 |
|---|---|
| `sites` 列数 | 11 → **56** ✅ |
| `orders` 出现 `site_cost`、`transactions` 出现 `site_id` | ✅ |
| 启动 SQL 报错 | **0 个** ✅ |
| 公开配置接口 | 正常返回 ✅ |
| 服务列表 | **2839 个**，且不含 `rate`（上游底价）✅ |
| 订单历史（生产管理员，19 单） | `status=success`，返回字段里**没有** `upstream_charge` / `site_cost` ✅ |
| 分站列表（0 个站） | `{"status":"success","data":[]}`，不是 500 ✅ |
| Beta 上再跑一次（表已齐全） | 「新增 0 列」—— 幂等，不会误加 ✅ |

### 以后怎么验：一条命令


## 二十五、自有域名 + 自动证书（85 期实测）

### 已经验过的

| 环节 | 实测结果 |
|---|---|
| 平台域不许被分站占用 | 绑 `shop85.taikon.top` → 被拒「免费子域名无需绑定，请填写你自己的域名」✅ |
| 域名格式校验 / 重复占用校验 | 代码内 `isValidDomain` + 双查 `domain`/`custom_domain` ✅ |
| DNS 没指过来时 | 返回 `pending` + 明确提示，并**给出本站专属 TXT 值**：<br>`xnow-verify=69111838a24082aa7b759ad0f022074a` ✅ |
| 此时不写 vhost / 不签证书 | 确认没有生成任何 nginx 配置文件与证书（域名还没通，写了也没用）✅ |
| 解绑 | vhost + Let's Encrypt 证书目录一并清掉，`nginx -t` 通过 ✅ |
| 免费子域名发布 | `{"message":"域名已生效（正式证书）","cert_mode":"letsencrypt"}` ✅ |
| 证书机本身 | `laozhang.taikon.top` 正挂着真实的 LE 证书（签发 Oct 24 → 到期 Jan 22），HTTPS 200 ✅ |

### 修掉的一个会误导站长的小问题

站长先点过「发布」（`cert_mode` 被写成 `letsencrypt`），接着绑自有域名但 DNS 没指过来，
状态是 `pending`，**界面上却还挂着「正式证书」** —— 他以为已经好了。
现在 `pending` 时会把 `cert_mode` 清空：

```
绑定前: cert_mode=letsencrypt status=active
绑定后: cert_mode=NULL        status=pending   ✅
```

### 唯一没法在这台机器上验完的一环

「DNS 已经指过来 → 自动跑 certbot 签正式证书」这一支，需要**一个真的指向本机 IP 的外部域名**。
目前祥哥的域名都在 Cloudflare 橙云后面，A 记录指向 CF 的 IP，不是本机 —— 所以归属验证会走 TXT 分支。
代码分支本身与「免费子域名发布」共用同一套 `ensureCert`（那套已经签出过真实证书）。

**他自己测的话，三步：**

1. 在「我的分站 → 自有域名」填域名并点绑定；
2. 按页面提示，在 DNS 加一条记录（二选一）：
   - 灰云/无 CF：`A` → 本机 IP
   - 橙云 CF：`TXT` → 页面上给出的 `xnow-verify=...`
3. 回后台点一次「修复域名」，看到「域名已开通，证书已自动签发 ✅」即成功。

⚠️ Let's Encrypt 对同一组域名有**每周 5 张**的签发限制，测试时别反复连点。

### 这一轮撞到的三个真问题（都已修）

1. **`req.user` 里没有 `agent_expire_at`** —— 鉴权中间件只查了 5 个字段，
   `req.user.agent_expire_at` 是 `undefined`，判断被静默跳过 →
   **代理过期的人照样能开新站，还被成功扣了 ¥99**。
   修法：中间件带上 `balance` / `agent_expire_at`，建站时再按数据库 role 复核。
2. **`sites.status` 是 ENUM('active','suspended')** —— 写 `expired` 直接
   `Data truncated for column 'status'`，到期停站静默失败。
   修法：模型加 `expired`，并在 app.js 里幂等 `MODIFY COLUMN` 扩老库 ENUM。
3. **墓碑配置引用不存在的证书** —— 写死 `/etc/nginx/ssl/<域名>.crt`，
   而分站用的是 Let's Encrypt（在 `/etc/letsencrypt` 下）→ `nginx -t` 失败 →
   reload 被跳过 → 墓碑根本没生效，到期站还能正常打开。
   修法：墓碑按「LE → 自签 → 平台兜底证书」顺序挑真实存在的证书；
   停站时先删真实 vhost 再立墓碑（否则两个同名 server 打架）。
   （另外我自己写的 `restoreSiteDomain` 用了相对路径 `client/dist`，
   把 vhost 的 root 写坏导致首页 500 —— 已改绝对路径。）

## 三十一、自有域名：生产 .env 从来没有 SERVER_PUBLIC_IP（91 期补上）

### 隐患

「自有域名自动证书」这条链路有两处依赖机器公网 IP：

| 用途 | 代码位置 | 没配的后果 |
|---|---|---|
| 告诉站长 A 记录该解析到哪 | `GET /api/sites` 的 `dns_target_ip` | 面板上不显示 IP，站长不知道往哪指 |
| 判断"域名是否已指向本机" | `verifyDomainOwnership()` | 只能走 TXT 校验，走不了"A 记录已就绪就自动签证书"这条顺路 |

而**生产的 `server/.env` 里根本没有 `SERVER_PUBLIC_IP`**（Beta 有）。上线脚本
`deploy-prod.sh` 也从来不会写它 —— 上线当天这条链路就是"半跛"的。
（历史原因：65 期为了不让公网 IP 进 PUBLIC 仓库，把源码里的硬编码 IP 拿掉了，
改成只认环境变量，但没人负责把它写进生产 .env。）

### 改法（三层兜底，IP 不进代码库）

1. **代码**：`siteDomain.js` 新增 `getPublicIp()`，取值顺序
   `process.env.SERVER_PUBLIC_IP` → `configs.server_public_ip`（后台可改）→ 空字符串。
   `verifyDomainOwnership()` 与 `/api/sites` 的 `dns_target_ip` 都改用它。
   取不到就返回空 —— 前端提示"问平台要地址"，不编一个错 IP 让站长白折腾，
   也不影响 TXT 校验这条路。
2. **上线脚本**：`deploy-prod.sh` 在备份 .env 之后幂等补一次：
   已有就跳过；没有就用 `ip route get 1.1.1.1`（**不发外网请求**，机器不通外网也能取）取本机出口 IP
   写进 `server/.env`，取不到只告警、不中断上线。`--dry-run` 下只打印将要写入的值。
3. **后台兜底**：换机/漏配时，往 `configs` 写一行 `server_public_ip` 即可生效，不用重启。

### 实测（Beta，三种取值情况都跑了）

```
① 环境变量在时        → "192.129.210.52"
② 删掉环境变量、无配置 → ""                （前端改成"问平台要地址"，不瞎指）
③ 后台配置里写上 IP    → "203.0.113.9"      （兜底生效）
```

## 三十五、客户分组价：不同客户不同价（93 期，祥哥「可以自定义可以百分比」）

### 一、做了什么

站长现在能给自己店里的客户**分档定价**，两种方式都支持：

| 方式 | 粒度 | 说明 | 优先级 |
|------|------|------|--------|
| **分组百分比** | 一组客户 | 建 VIP / 老客户等分组，每组一个折扣（9 折 = 90%） | ② |
| **单独自定义** | 单个客户 | 某个客户单独给一个折扣，覆盖分组 | ① |

**价格链路（三处必须同口径，已经全部对齐）**：

```
平台底价 × 站长倍率 × 站点活动折扣 × 客户分组/单独折扣  →  与「站长成本」取大（红线）
```

- `orders.js`：真正扣钱的地方（权威）
- `services.js`：客户在页面上看到的价格（显示）
- 两处调用同一个 `customerDiscountMultiplier()`，杜绝"看到的价 ≠ 扣的价"

### 二、库表（启动自动补，不需要手工迁移）

```sql
CREATE TABLE site_customer_groups (
  id, site_id, name, multiplier DECIMAL(5,3) /* 0.300~1.000 */, note, timestamps
);
ALTER TABLE users ADD COLUMN site_group_id INT DEFAULT NULL;
```

⚠️ 踩坑记录：`users.site_group_id` **必须**同时写进 `models/User.js` 的属性声明。
只在库里加列、模型里不声明 → Sequelize 读出来是 `undefined`，分组价静默失效
（本轮实测就是这样：入组成功、显示价却不动；补上声明后立刻正常）。

### 一、为什么要做自检脚本

`AUDIT_WRITE=1` 才做真实写入（切模板色系、真下单、域名探测），且会自动复原。

## 三十七、未知子域名兜底：不再把平台暴露给客户（95 期）

### 一、发现的问题（严重，直接踩红线）

`*.taikon.top` 是泛解析。任何**没有自己 vhost** 的子域名，以前会落到 nginx 的「默认 server」，
访客看到的是**主站首页**：

```
修复前：
  https://fresh-never-visited-95.taikon.top/  → HTTP 200，页面里 19 处 XNOW
```

三类真实后果：

| 场景 | 客户会看到什么 |
|------|----------------|
| 站长把子域名改掉 / 站点过期 / 被删 | 收藏的旧域名 → **平台主站** |
| 站长把域名一个字母打错 | 客户 → **平台主站** |
| 客户手输域名出错 | 客户 → **平台主站** |

等于把「平台上还有一层」直接展示给分站客户 —— 违反「客户永远不知道主站存在」。

另外还有一个 70 期记录、**从未执行**的老坑：`xnow-beta` 的 `server_name` 里有
`*.xnow.taikon.top`，未知的 xnow 子域名会落到 **Beta 实例**（那是另一个数据库）→
订单与余额会和生产串库。

### 二、修法

新增 `deploy/sites/nginx-catchall.conf`（80 + 443 各一组）：

```nginx
# 主站自己的名字：照旧 301 到 HTTPS
server { listen 80; server_name xnow.taikon.top taikon.top www.taikon.top;
         location ^~ /.well-known/acme-challenge/ { root /var/www/acme-challenge; }
         location / { return 301 https://$host$request_uri; } }

# 其它所有子域名（80 与 443 各一份）：中性 404
server { listen 80;             server_name *.taikon.top *.xnow.taikon.top;  return 404 '…页面不存在…'; }
server { listen 443 ssl http2;  server_name *.taikon.top *.xnow.taikon.top;  return 404 '…页面不存在…'; }
```

三个关键点：

1. **用通配，不动 default_server** —— nginx 优先级 = 精确 > 最长通配 > default_server，
   所以只影响「没有站点占用的子域名」，主站与每个分站的精确 vhost **一个字没改**。
2. **80 和 443 都要写** —— Cloudflare 是连源站 443 的，只改 80 完全挡不住（本轮实测踩过：
   改完 80 后公网仍然返回主站）。
3. **主站名字必须显式列进 301 块** —— 80 端口上主站本来靠 default_server 兜着，
   一旦出现 `*.taikon.top` 通配，`xnow.taikon.top` 会优先匹配通配变 404；
   若 Cloudflare 走 Flexible 模式，主站会立刻全站挂。

配套：去掉 `xnow-beta` 里的 `*.xnow.taikon.top`（由 `deploy/sites/deploy-catchall.sh` 做，
幂等、带备份、带回滚命令）。`deploy-prod.sh` 第 6 步已改为调用它，
并在第 7 步自检里加了一条「未分配域名必须 404」。

## 三十九、改价体验重做 + 拔掉「倍率」这个泄露口（97 期）

### 一、祥哥指出的问题

> 「你这样站长不就知道我的成本价了吗，这个价格修改窗口太小了吧，操作修改都不方便呀，有更好的方案吗」

两件事，都是硬伤：

**① 站长能反推出平台加价**。改价页当时写着：
> 成本 ¥172.80 / 千 · 默认售价 ¥259.20 / 千 · 毛利 33.3%
> 成本保护线 **2 倍** · 当前全场 **3 倍**
> 「3 倍 = 客户看到的价格是平台基础价的 3 倍。**你的进价约是基础价的 2 倍**，客户付 3 份、你付 2 份」

售价 = 基础价 × 3，进价 = 基础价 × 2 —— 两个数一除就是 **1.5**，再配上「3 倍」，站长立刻知道
「平台在基础价上加价 100%」。设太低时的报错更直白：
> 「你从平台的进价是 **2 倍**（全局 **2.5** × 你的折扣 **0.8**）」

这等于把进货加价倍数、全局倍率、代理折扣三个数字全给了他。

**② 改价窗口太小**。每条服务右侧是个 7 字符宽的小输入框，一行行敲；200 条刷粉服务要改价，
手机上基本没法用。

### 二、方案：前端彻底不谈「倍率」，只谈「加价率」

站长真正需要知道的是**他自己的两个数字**：进货价、卖多少。所以：

| 以前（泄露） | 现在 |
|---|---|
| 售价倍率 5 倍 / 成本保护线 2 倍 | **加价率 150%**（在进货价上加 150%） |
| 「你的进价是基础价的 2 倍」 | 不出现 |
| 报错：「你从平台的进价是 2 倍（全局 2.5 × 折扣 0.8）」 | 「售价不能低于你的进货价，那样每单都亏。请把加价率设为 0% 或更高」 |
| API 回传 `multiplier` / `cost_multiplier` / `min_multiplier` | **全部不再回传**，只回 `markup_pct` |

加价率 = 售价 ÷ 进货价 − 1，只涉及站长自己的两个数字 —— 他怎么算都推不出平台在基础价上加了多少。
换算在后端做：`倍率 = 进价倍率 × (1 + 加价率)`，站长永远看不到这一步。

实测（Beta 站点 25，进货价 ¥25）：
```
加价率 150%  → 首条售价 62.50   （25 × 2.5）
加价率 100%  → 首条售价 50.00   （25 × 2.0）
加价率 -5%   → 拒绝：「加价率不能低于 0%（0% = 按进货价卖，不赚不亏；再低就亏本了）」
站点接口     → 无 multiplier / min_multiplier；价格页 meta 无 multiplier / cost_multiplier
建站（80%）  → 首条售价 45.00   （25 × 1.8，换算正确）
```

### 三、改价交互重做（手机优先）

**点一条 → 从底部弹出大面板**：
- 输入框 24px 大字，占满宽度，不用找
- 快捷价：`进货价 ¥25.00`、`+20%`、`+50%`、`×2` —— 一按即填，不会算错
- 实时显示：客户实付 ¥… / 你赚 ¥…（毛利 …%），低于进货价当场标红
- `跟随全场` 一键清空覆盖、`确定` 回到列表

**整类一键定价**（新增）：

- 填完仍可单条微调，最后统一「保存定价（N 项）」

```

   演示站 API  → 502     ← 真相：后端已经死了

③ 回滚（--code-only）

   ✅ pm2 online

④ 复核
   坏代码残留 0 处 · 数据库未被动过（站点 3 / 用户 8 / 订单 0）· API 200
```

### 二、演练抓到的两个真问题

**① 「首页 200」不能当健康判据。**
后端已经 502 了，`https://demostore.taikon.top/` 照样返回 **200** —— 因为首页是 nginx 直接给的静态 HTML，
只有 `/api/*` 走代理。**只探首页会以为一切正常。** 判据必须是 `/api/public/config`。

**② 脚本推荐的回滚命令是「会丢数据」的那条。**
`deploy-prod.sh` 结尾原来推荐：
```
bash rollback-sites.sh --env prod --stamp XXX      ← 连数据库一起还原
```
上线后已经产生的真实订单/用户/充值会**全部消失**。出问题时的第一反应必须是「只回滚代码」，库只在代码回滚后仍不行时才动。已改成：

```
回滚第一步（绝大多数情况只做这一步，不动数据库）:
  bash rollback-sites.sh --env prod --stamp XXX --code-only

⚠️ 只有在代码回滚后仍然坏掉时，才考虑连库一起还原（会丢上线后新增的订单/用户）
```

顺手还改了回滚脚本的自检标签：原来写死「主站首页 / 主站 API」，`--env beta` 演练时看着像探错了环境，现在跟着环境走；并在注释里写明「首页 200 不等于健康」。

### 三、另一个上线前的坑：CRLF 会把脚本废掉

从 Windows 直接 scp 上去的 `.sh` 是 CRLF，bash 直接报 `syntax error near unexpected token 'in\r''`。
git 里存的是 LF，`go-live.sh` 用 `git show` 取出来的也是 LF —— 所以正常路径没问题，
但**任何人手工 scp 脚本时必须先去掉 CR**，否则回滚这条命脉就断了。已实测确认修好后可正常执行。

## 四十四、上线前发现的一个跨环境地雷：域名空间共用（101 期）

### 一、问题

Beta 和生产在**同一台机器**上，共用：

- `/etc/nginx/sites-enabled` 这一套 nginx 配置目录
- `*.taikon.top` 这条泛解析（Beta 的 `demostore.taikon.top` 就是这么来的）
- 免费子域名自动生成的母域（`SITE_DNS_SUFFIX` 默认 `taikon.top`）

但**两边的数据库是分开的**。于是有个漏洞：

> 生产上如果有个代理把分站域名填成 `demostore.taikon.top`（这正是 Beta 在用的），
> 建站校验只查「自己库里有没有这个域名」——查不到，放行。
> 然后两份 vhost 抢同一个 `server_name`，nginx 只认先加载的那份。
> 结果：这个域名的客户可能被送进**另一个环境的数据库**，看到别人的价格、别人的订单。

现在的实际状态：机器上有 3 条 vhost（`laozhang` / `t1` / `demostore`），都是 Beta 的。
生产一旦上线，第一个代理只要手抖填了这三个名字中的任意一个，就会踩中。

### 二、修法：查 nginx 目录，而不是只查自己的库

新增 `domainVhostOwner(domain, selfSiteId)`：扫 `/etc/nginx/sites-enabled/`，
找「同一域名但不是本站在用」的 vhost 文件。

两处接上：

1. **建站**：免费子域名如果已被任何 vhost 占用 → 直接拒绝「这个域名已经被占用了，请换一个」
2. **自动分配**：随机 6 位子域名循环里，除了查库，还要求 nginx 目录里没有同名 vhost

自己的 vhost 传 `selfSiteId` 放行，所以「修复域名」不受影响。

### 三、实测

```
① 建站填 demostore.taikon.top（Beta 在用） → ✅ 被挡「这个域名已经被占用了，请换一个」
② 建站填 laozhang.taikon.top（Beta 在用）  → ✅ 被挡（同上）
③ 建站填 brandnew98.taikon.top（全新域名）  → ✅ 通过域名校验（故意传非法加价率，死在加价率那步，说明没被误挡）
④ 站点数 1 → 1（没有产生任何脏数据）
⑤ 自家站点「修复域名」/publish            → ✅ 域名已生效（正式证书），演示站与 API 均 200
```

### 四、上线后的注意事项（写给以后维护的人）

- 生产上线后，**Beta 那 3 个域名仍然占用着**。要么 Beta 保持现状（推荐，便于随时对照），
  要么等生产稳定后把 Beta 的站点删掉腾出域名。
- 更彻底的做法是让两个环境用不同的子域空间（Beta 用 `*.beta.taikon.top`），
  但这要改泛解析 + 证书，且 Beta 只是临时环境，暂不做。

## 四十五、自有域名也撞车 + 补上「手动加余额兜底」（102 期）

### 一、上一轮的防护有缺口：只挡了免费子域名

101 期加的 `domainVhostOwner` 只接在「免费子域名」那条路上。但**自有域名同样会撞**：
同一个 `shop.xxx.com` 在 Beta 和生各绑一次，两份 vhost 抢一个 `server_name`，结果一样糟。

补在两处：

- **绑定自有域名** `POST /api/sites/:id/domain`：库查重之后再加一道 nginx 级检查
- **建站**：把检查从「只查免费子域名」扩到所有域名

实测（造一个「nginx 有 vhost、两个环境的库里都没有」的域名 `guardtest98.example.com`）：

```
① 绑该域名 → ✅「这个域名已经被占用了，请换一个」（库查重根本查不到它，是 nginx 级检查挡住的）
② 建站用同域名 → ✅ 同样被挡
③ 清理假 vhost 后 nginx -t 正常；站点 25 未受影响，「修复域名」仍成功
```

### 二、目标里「手动加余额兜底」原来是缺的

方案② 是「钱进站长自己的商户」。但站长**刚开站、商户还没配好**时，客户怎么付款？
最常见的就是：客户微信直接转给站长 → 站长得能把这笔钱记到客户账上，否则客户下不了单。

翻了一遍代码：**没有这个功能**。站长只能改折扣，不能动余额。补上。

**接口**（两个，都落流水）：

| 接口 | 作用 |
|---|---|
| `POST /api/sites/:id/customers/:uid/balance` | 加余额（客户线下转账后记帐） |
| `POST /api/sites/:id/customers/:uid/balance/deduct` | 扣回（加错了 / 退款） |

护栏：只能操作自己分站的客户、金额必须 > 0、单笔上限 ¥100000、扣减不能超过客户余额、
流水 `site_id` 必须写本分站（否则平台营收会被算多）。

**界面**：客户面板里新增「💳 手动加余额」——当前余额、`¥10/¥50/¥100/¥200` 快捷金额、
大字金额输入、备注、加余额 / 扣回。手机上一屏点完。

### 三、测试里抓到一个真 bug（已修）

第一版写完就测，结果：

```
① 加 ¥25.50 → "加余额失败：Transaction is not defined" · 但客户余额真的变成 ¥75.50
```

**钱到账了、流水没落**——半截写入，对账时查无此事。两个原因：
1. `Transaction` 没导入
2. 余额 `save()` 和流水 `create()` 是两条独立语句，前成功后失败就成这样

修法：补导入，并把两步包进**同一个数据库事务**。复测：

```
① 加 ¥25.50 → success · 余额 ¥50 → ¥75.50
② 扣回 ¥25.50 → success · 余额 ¥75.50 → ¥50.00
   流水两条都在：站长手动充值 +25.5 site_id=25 / 站长手动扣款 -25.5 site_id=25
```

**手机实测**（390px）：面板里「手动加余额」区块正常显示，点 `¥50` → 点「加余额」→ 余额 ¥50 → ¥100，
提示「已加 ¥50.00，当前余额 ¥100.00」，随后扣回复原 ¥50。

### 二、首页模块「排序」是假的（拖了没用）

顺手验「首页模块可开关排序」时发现：**开关是好的，排序完全无效**。

实测：库里把「热门服务」的 order 改成 3、「数据统计」改成 4，等 70 秒越过 60s 站点缓存，
页面上的统计卡仍在上、热门服务仍在下。

根因：`order` 是 CSS 属性，**只在同一个父容器的兄弟之间生效**。

- 公告 / 数据统计 / VIP / 返佣 → 渲染在 `SiteModules.vue`，外面套了一层自己的 `max-w-5xl` 容器
- 热门服务 / FAQ / 优势 / CTA / 适用人群 → 渲染在 `Home.vue`，是根容器的另一批子元素

两个容器各排各的，所以站长把「热门服务」拖到最上面，那一块的 order 只在 Home 的那批兄弟里生效，
永远跳不到 SiteModules 那批的前面 —— 表现为「拖了没反应」。

修法：把 `SiteModules` 自带的容器去掉，每块外包一层只负责对齐宽度的壳（`w-full max-w-5xl mx-auto px-6`），

实测：

```

改回 stats(3) / hot(4)          → 统计卡 y=749、热门服务 y=844   ✅ 复原生效

```

### 二、顺手把「改完找不到保存」这整类问题一次解决

- 保存成功 → 快照刷新 → 浮条自动消失
- 订单页 / 客户价页不显示（那两页没有表单）
- 浮条右侧留 96px 避让：右下角的 LIVE 客服球原来正好压住保存按钮（实测坐标：
  按钮右边缘 257px、客服球左边缘 310px，现在 `重叠: false`）

### 三、这一步里踩的坑（记下来，别再犯）

第一版浮条死活不出现。原因：给 `load()` 加的 `await nextTick()` 用到了 `nextTick`，
但 `import { ref, computed, onMounted, watch } from 'vue'` **没有加 nextTick**；
而补丁脚本判断「是否已导入」时，搜的是整个文件（此时文件里已经有我插入的 `nextTick()` 调用），

教训：**补丁脚本判断依赖是否已导入，要看 import 那一行，不要搜全文。**

- 平台侧（admin / super_admin）不受影响

### 现在


### ② 备份真空洞：换服务器会丢两样东西

原来备份包只有 `xnow_db.sql` + `pending_payments.json`：

| 丢什么 | 后果 | 严重度 |
|---|---|---|
| `uploads/`（站长上传的背景图/logo） | 数据库只存 `/uploads/xxx.png`，图没了 → 分站页面白底 | 高 |
| 分站 nginx vhost（每个自有域名一个） | 自有域名全部 404，而子域名正常 → **极难发现** | 高 |

现在是四件套：`xnow_db.sql` + `pending_payments.json` + `uploads/` + `nginx-sites/`，
还原时各回原位（vhost 写回后自动 `nginx -s reload`）。

Beta 实测闭环：
```
备份 → 成员 xnow_db.sql / pending_payments.json / uploads/(2) / nginx-sites/(4)
删掉一张图 → restoreBackup → 文件回来；数据库分站客户数仍为 3
```

### ③ 顺手修掉的环境隔离泄漏

`BACKUP_DIR` 原写死 `/var/www/xnow/backups` → **Beta 定时备份会写进生产备份库**。

实测：Beta 备份后生产目录仍是 24 份。

### ④ 兜底脚本 `deploy/sites/rebuild-vhosts.cjs`

## 七十二、「我的分站」按角色改名（110 期，祥哥指出）

祥哥：「这个我的分站不是站长看的吧，是主站管理员看的吧，是不是应该叫分站管理」。

确实是个语义 bug：这一项对**员工（admin/super_admin）**列出的是**全部分站**
（`GET /api/sites` 对 staff 返回全量），但标题写「我的分站」，超管看着会以为是自己开的店。

改成跟着角色走：

| 角色 | 侧边栏 | 页面标题 | 站点列表标题 | 角标 |
|---|---|---|---|---|
| admin / super_admin | **分站管理** | 分站管理（全部站点的运营情况） | 全部分站（N 个） | 不显示 ¥99/月 |
| user / gold / agent | 我的分站 | 我的分站（改名字、换模板…） | 我的分站（N 个） | 未开站时显示 ¥99/月 |

实测：
- 超管：标题「分站管理」，侧边栏「分站管理」，列表「全部分站（4 个）」
- 普通用户 uid 103：标题「我的分站」，侧边栏「我的分站 ¥99/月」

> 员工点列表里的站仍然进同一个后台（切过去 = 以管理员身份管这个站），
> 只是入口名字不再误导。
